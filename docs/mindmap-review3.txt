# 증권사 리포트 → 투자 마인드맵 설계 v3 필수 수정사항

첨부하신 설계 v3 원문과 쉬운 해설 Word 문서를 함께 검토했습니다.

이번에는 기능을 더 추가하자는 제안은 제외하고, 현재 설계대로 구현하면 잘못된 투자정보가 생성되거나, 검증·업데이트 과정에서 구조적인 오류가 발생할 수 있는 사항만 선정했습니다.

제 판단으로는 반드시 수정해야 할 사항 10개가 있습니다. 이 중 1\~6번은 해당 기능을 개발하기 전에 해결하는 것이 좋겠습니다.

## 1. 필수 수정사항 우선순위

| 우선순위 | 반드시 수정할 내용               | 문제가 되는 이유                    |
| ---- | ------------------------ | ---------------------------- |
| P0-1 | Claim의 사실·전망·가정 구분 강화    | 전망을 확정 사실처럼 표현할 위험           |
| P0-2 | Claim 검증과 승인 기준 강화       | 잘못된 주장도 원문 검증을 통과할 가능성       |
| P0-3 | Issue의 동의·반대 판정 기준 명확화   | 증권사 간 공통 견해와 이견이 왜곡될 위험      |
| P0-4 | 재무 수치의 비교 가능성 검증 강화      | 서로 다른 기준의 수치를 평균할 위험         |
| P0-5 | 시나리오 후보와 실제 시나리오 구분      | 목표주가를 Bear/Base/Bull로 오인할 위험 |
| P0-6 | 자동 Kill 조건 생성 기준 강화      | 투자 판단에 잘못된 종료 조건 적용 위험       |
| P1-1 | 신규 리포트 업데이트의 정합성 보장      | 서로 다른 시점의 분석값이 혼합될 위험        |
| P1-2 | LLM 실패 시 품질·사용 제한 명확화    | 저품질 결과가 정상 분석으로 사용될 위험       |
| P1-3 | P2.5 최소 실험과 P3·P4 의존성 수정 | 개발 단계의 완료 기준을 충족할 수 없음       |
| P1-4 | 골든 데이터 평가 기준 강화          | 실제 성능보다 정확도가 높게 측정될 위험       |

## 2. 반드시 수정해야 할 핵심 6개 항목

### P0-1. Claim의 사실과 예측을 더 명확히 구분해야 합니다

현재 v3는 Claim에 `epistemic_type = fact | estimate | opinion`을 둡니다.

좋은 방향이지만 실제 증권사 리포트에는 다음과 같은 차이가 있습니다.

| 문장                            | 올바른 해석        |
| ----------------------------- | ------------- |
| 삼성전자가 신규 설비투자 계획을 발표했다        | 발표 사실         |
| 삼성전자가 2027년에 공급량을 30% 늘릴 전망이다 | 증권사 예측        |
| 삼성전자가 공급량을 30% 늘릴 계획이라고 밝혔다   | 기업의 계획에 대한 사실 |
| 공급량이 증가하면 영업이익이 개선될 것이다       | 조건부 전망        |

세 번째 문장은 발표했다는 사실은 맞더라도 공급량 증가가 실제로 발생했다는 뜻은 아닙니다.

반드시 수정할 사항: Claim에는 `epistemic_type` 외에도 `asserted_by`(누구의 주장인가), `certainty`(확정·예정·가능성), `as_of_date`(언제 기준의 정보인가)를 구분해야 합니다.

그렇지 않으면 마인드맵에서 증권사 예상과 기업 발표, 이미 발생한 실적이 섞일 수 있습니다.

### P0-2. Claim 검증 결과를 LLM 판정만으로 확정하면 안 됩니다

v3는 원문 존재, 숫자 일치, 의미 지지의 3단계를 거쳐 Claim을 `verified`로 만듭니다.

구조는 타당합니다. 다만 의미 지지를 별도 LLM이 확인했다고 해서 주장의 의미적 정확성이 확정되는 것은 아닙니다.

특히 추출 LLM과 검증 LLM이 동일한 문장을 같은 방식으로 잘못 해석할 수 있습니다.

반드시 수정할 사항: 검증 결과를 두 가지로 분리해야 합니다.

- `machine_verified`: 자동 검증을 통과한 상태
- `human_verified`: 사람이 직접 승인한 상태

모든 Claim에 사람 승인을 요구할 필요는 없습니다. 자동 검증을 통과한 Claim은 근거가 표시된 초안에 사용할 수 있습니다.

다만 출처가 충돌하거나 숫자가 중요한 투자 판단에 직접 영향을 주는 Claim은 사람 검토 대상으로 올려야 합니다.

또한 자동 검증에서 `insufficient` 판정을 받은 Claim은 사람이 승인하더라도 승인 이유와 근거를 기록해야 합니다.

### P0-3. Issue의 '동의·반대' 판정이 모호합니다

현재 v3에는 다음 필드가 있습니다.

`coverage = {broker: mentioned | agree | disagree | silent}`

문제는 무엇에 동의하거나 반대하는지 기준이 명확하지 않다는 점입니다.

예를 들어 한 증권사가 HBM4 공급 증가를 긍정적으로 전망하고, 다른 증권사가 공급 증가를 예상하면서도 수익성에는 부정적인 영향을 줄 수 있다고 분석할 수 있습니다.

둘 다 공급 증가에는 동의하지만 이익 효과에 대해서는 다른 견해입니다.

따라서 Issue별로 비교 대상을 하나의 명제로 명확히 정의해야 합니다.

반드시 수정할 사항: 각 Issue에 `reference_proposition`을 추가하고, 증권사별 판정은 해당 명제에 대해서만 수행해야 합니다.

또한 `silent`는 전체 리포트에서 확인되지 않았다는 뜻과, 분석한 청크에서 발견되지 않았다는 뜻을 구분해야 합니다.

이는 v3의 가장 중요한 기능인 증권사 간 이견 분석의 정확도와 직접 연결됩니다.

### P0-4. 수치 집계에서 단순한 basis 태그만으로는 부족합니다

v3는 연결·별도, 지배주주·전체 기준이 같은 수치만 평균하도록 했습니다.

하지만 실제로는 다음 항목까지 비교해야 합니다.

- 같은 기업·사업부 범위인가?
- 같은 회계기간인가?
- 실적 확정치(A)인가, 잠정치(P)인가, 추정치(E)인가?
- 영업이익과 조정 영업이익이 혼합되지 않았는가?
- EPS 계산의 주식 수와 주식 종류가 동일한가?
- 단위와 환율 적용 기준이 같은가?

특히 같은 증권사의 최신 리포트라고 해도 모든 연도와 재무 항목의 추정치가 들어 있는 것은 아닙니다.

최신 보고서가 특정 분기 실적만 다루는 경우에는 이전 보고서의 장기 추정치가 여전히 유효할 수 있습니다.

반드시 수정할 사항: '증권사별 최신 리포트 1건'을 기본 대표 문서로 사용하되, 실제 집계는 `증권사 × 지표 × 대상 기간 × 회계 기준`별 유효한 최신 추정치를 선택하도록 설계해야 합니다.

그렇지 않으면 최신 리포트를 사용하면서도 일부 기간의 컨센서스가 누락될 수 있습니다.

### P0-5. 증권사별 가치평가 후보는 곧바로 Bear/Base/Bull이 아닙니다

v3에서는 같은 증권사 내부의 EPS와 PER을 사용해 목표주가를 계산하고, 사용자가 Bear/Base/Bull 후보로 넣도록 합니다.

서로 다른 증권사의 가정을 섞지 않는다는 점은 옳습니다.

그러나 A증권사의 목표주가가 40만 원이고 B증권사가 50만 원을 제시했다고 해서 A를 Bear, B를 Bull로 분류할 수는 없습니다.

두 증권사 모두 자신들의 목표주가를 기준 시나리오로 제시했을 수 있기 때문입니다.

반드시 수정할 사항: 다음 객체를 분리해야 합니다.

| 데이터              | 의미                      |
| ---------------- | ----------------------- |
| Broker Valuation | 증권사별 기준 목표주가            |
| Broker Scenario  | 증권사가 명시한 Bear/Base/Bull |
| User Scenario    | 사용자가 직접 확정한 시나리오        |

사용자가 증권사별 기준 목표가를 Bear나 Bull에 배치할 수는 있지만, 이 경우에는 사용자가 재해석한 시나리오라는 기록을 남겨야 합니다.

목표가 범위만으로 세 시나리오를 자동 완성하지 않는 v3 원칙은 그대로 유지해야 합니다.

### P0-6. 리포트의 조건부 위험을 자동 Kill 조건으로 변환하는 것은 위험합니다

v3는 수치가 있는 조건부 리스크 Claim에서 Kill 조건을 자동 제안하도록 했습니다.

예를 들어 리포트에 다음과 같은 표현이 있다고 하겠습니다.

> 생산 수율이 60%에 미달하면 수익성 개선이 지연될 수 있다.

이를 바로 `yield < 60%`라는 Kill 조건으로 바꾸는 것은 문제가 있습니다.

수익성 개선 지연과 투자 논제 붕괴는 다른 개념입니다. 수율이 일시적으로 낮아져도 장기 투자 논제가 유지될 수 있기 때문입니다.

반드시 수정할 사항: 자동 생성 단계에서는 `Risk Trigger Candidate`까지만 만들고, 실제 Kill 조건은 사용자가 별도로 확정하도록 해야 합니다.

또한 실제 관측 가능한 KPI인지, 데이터 업데이트 주기가 무엇인지, 조건을 위반했을 때 어떤 행동을 할지도 별도로 정의해야 합니다.

## 3. 개발·운영 단계에서 반드시 수정할 4개 항목

### P1-1. 신규 리포트 반영은 노드별 업데이트만으로 부족합니다

현재 ChangeSet은 변경 전후 노드와 근거를 저장하고, 사용자 승인 후 적용합니다.

그러나 A1의 컨센서스가 바뀌면 A2의 이견, A3의 가치평가, A4의 리스크 등 여러 노드가 함께 영향을 받을 수 있습니다.

따라서 노드 일부만 승인했을 때 마인드맵 내부의 분석 시점이 섞일 수 있습니다.

수정 방향: ChangeSet에 `input_snapshot_id`, 영향받는 노드 목록, 의존성 관계를 포함해야 합니다. 승인 전 전체 마인드맵을 검증하고, 버전 저장은 원자적으로 처리해야 합니다.

### P1-2. LLM 실패 시 기존 규칙 방식으로 전환하는 범위를 제한해야 합니다

v3는 LLM이 동작하지 않으면 기존 키워드 분류로 폴백하고 `quality="rules"`를 표시합니다.

하지만 키워드 기반 문장 분류는 이미 실제 리포트에서 잘못된 리스크를 추출하는 문제가 확인됐습니다.

따라서 단순히 '저품질' 표시만 붙여 정상 마인드맵을 생성하는 것은 적절하지 않습니다.

수정 방향: 규칙 모드에서는 PDF 메타데이터, 수치 컨센서스, 목표주가 분포 등 결정론적으로 검증할 수 있는 내용은 생성하되, Claim/Issue 기반 투자 논제와 이견 분석은 '미검증 초안' 또는 '생성 불가'로 제한하는 것이 안전합니다.

### P1-3. P2.5 개발 단계의 선후 관계가 맞지 않습니다

이것은 문서에서 확인되는 명확한 구현 계획상의 문제입니다.

v3는 P2.5에서 삼성전자 리포트 3건을 사용해 공통 논거, 핵심 이견, A0\~A8 마인드맵 초안까지 평가하도록 합니다.

그러나 해당 기능의 정식 구현은 각각 P3(Issue 통합)와 P4(맵 생성)에 배정되어 있습니다.

즉, P2.5 완료 기준이 아직 개발하지 않은 기능을 요구하고 있습니다.

수정 방향: P2.5는 Claim 추출 정확도만 검증하는 관문으로 변경하거나, P3·P4의 최소 기능을 먼저 만드는 통합 실험으로 명시해야 합니다.

저는 후자를 권합니다. 삼성전자 3건으로 실제 마인드맵을 만든 후 본격 구현에 들어가는 편이 효율적입니다.

### P1-4. 평가 목표가 높게 나와도 실제 품질이 검증되지 않을 수 있습니다

v3의 목표는 Claim 재현율 80%, 근거 불일치율 5% 이하, Issue 정답 일치율 80% 이상입니다.

그러나 현재 평가에 사용하는 리포트는 13건이고, 이 데이터는 프롬프트와 정규화 사전을 개발할 때에도 사용됩니다.

같은 데이터로 개발과 평가를 반복하면 해당 리포트에만 잘 작동하는 시스템이 될 수 있습니다.

수정 방향: 13건은 개발·회귀 테스트 데이터셋으로 사용하고, 별도의 미사용 리포트로 최종 검증해야 합니다. 또한 근거 불일치율뿐 아니라 유효하지 않은 Claim이 승인되는 비율과 중요한 이견을 놓치는 비율도 측정해야 합니다.

## 4. 제가 권하는 최종 수정 순서

1단계 — 데이터 계약 수정

Claim·EvidenceSpan·Issue·Consensus의 데이터 모델을 확정합니다. P0-1부터 P0-4까지 해결합니다.

2단계 — 시나리오와 Kill 의미 수정

P0-5, P0-6을 해결하고 증권사의 전망과 사용자의 의사결정을 분리합니다.

3단계 — 업데이트·폴백·개발 계획 보완

ChangeSet의 정합성, 규칙 모드의 제한, P2.5의 선후 관계를 수정합니다.

4단계 — 삼성전자 3건으로 통합 검증

Claim, Issue, 숫자 집계, A0\~A8 생성까지 실제 산출물을 확인합니다. 그 결과를 기준으로 전체 구현에 들어갑니다.

## 최종 의견

현재 v3는 전체 아키텍처를 다시 만들 필요는 없습니다. 기존 코드 재사용, Claim/Issue 도입, 출처 검증, 사용자 승인이라는 기본 방향은 유지하는 것이 좋습니다.

가장 먼저 수정해야 할 세 가지를 고른다면 다음과 같습니다.

1. Claim의 의미와 근거 검증 정확도: 잘못 해석된 내용이 자동으로 확정되지 않도록 합니다.
2. Issue의 증권사 간 비교 정확도: 같은 테마를 언급한 것과 실제로 같은 전망을 한 것을 구분합니다.
3. 컨센서스 및 시나리오의 수치적 정합성: 서로 다른 기준이나 가정을 임의로 섞지 않도록 합니다.

이 세 가지가 잘못되면 나머지 기능이 정확히 동작해도 투자자가 신뢰하기 어려운 마인드맵이 만들어집니다.

반대로 이 세 가지를 해결하면, 증권사 리포트 여러 건을 읽고 핵심 투자 논거와 이견을 정확하게 비교해 주는 시스템이라는 본래 목적에 상당히 가까워질 수 있습니다.
