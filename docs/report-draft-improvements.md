## 3. 개선안 상세

각 항목: 문제 → 방법 → 설계 메모 → 확인 방법 → 비용·위험.

### A. LLM 그룹 채움을 실제로 쓰기, 문장 분류를 LLM 에 (우선 1)

**문제** 사용자 맵 3개 모두 `meta.llm: true` 였지만 그룹 6개가 전부 실패했고(인증), 내용은 규칙 채움이었다. 원인은 `.env` 의 `ANTHROPIC_API_KEY` 가 `apikey_…` 31자(Anthropic 형식 `sk-ant-…` 아님). 1차 수정으로 이제 실패가 **보인다**(요약 "LLM 0/6 그룹", 깃발, 대화상자 ⚠). 그리고 규칙 채움의 리스크·논거 선택은 키워드 점수라 결(긍/부정)을 잘 못 가른다.

**방법**
1. 키를 고치고 실제 리포트 13건으로 한 번 돌린다. 그룹 채움(drivers/thesis/scenarios/risks/catalysts/evidence) 이 리스크·논거를 **문장 단위로 다시 고르므로** 키워드 분류의 약점은 그 자리에서 대체된다.
2. 그 다음, 규칙 채움 단계의 문장 분류도 LLM 으로 바꾸는 작은 호출을 하나 둔다: 후보 문장 40~60개를 한 번에 보내 `{"id": n, "kind": "risk|thesis|catalyst|valuation|shareholder|business|none", "polarity": "+|-|0", "when": "2026-10-30|null"}` 를 받는다. 키워드 점수는 **후보 추리기**(prefilter) 로만 남긴다. 호출 1회, 비용 작음, 실패하면 지금 방식으로 폴백.
3. 환각 방어는 기존 그대로: 문장 id 만 받으니 지어낸 문장이 들어올 수 없다. 날짜(`when`)는 본문에 그 날짜 문자열이 있을 때만 수용.

**설계 메모** `reports/extract.py::extract_sentences` 는 그대로(후보 생성), `generate/llm_fill.py` 에 `classify_sentences(filler, sentences, materials)` 추가, `generate/draft.py` 의 규칙 채움 전에 선택적으로 호출. `MockGroupFiller` 에 분류 응답 추가해 테스트. 프롬프트는 `generate/prompts.py` 에 `CLASSIFY` 그룹으로.

**확인** 13건에 대해 사람이 매긴 정답표(리스크/논거/촉매 각 3~5문장) 와 일치율. 목표: 상위 3개 중 2개 이상 일치.

**비용·위험** 키 수정은 사용자 몫. 호출 1~2회/초안 추가. LLM 이 없으면 지금처럼 동작.

### B. 리서치 DB 교차 확인 (우선 2)

**문제** 제목·증권사·날짜·TP 를 PDF 본문에서 정규식으로 읽는다. 1차 수정 전에는 13건 중 제목 6건이 틀렸고, TP 도 '적정주가'(메리츠) 같은 표기 하나로 틀어졌다. 그런데 사용자가 받는 파일 이름이 `company_96425.pdf`, `삼성전자_96588.pdf`, `hk_652446.pdf` 처럼 **한경 리포트 id** 를 담고 있고, 리서치 DB `reports(report_id, stock_code, broker, title, posted_date, pdf_url)` + `report_details(opinion, target_price, prev_target_price)` 에 같은 리포트가 있다.

**방법** 파일명에서 `(\d{4,7})` 를 뽑아 `reports.report_id` 로 조회. 있으면
- 종목코드·증권사·날짜·제목·TP·직전 TP·의견을 **DB 값으로 채우거나**(본문에서 못 읽은 칸), **본문 값과 다르면 깃발**("TP 본문 330,000 / DB 320,000").
- 종목코드가 다르면(다른 종목 리포트가 섞임) 즉시 경고 — 지금은 본문 코드로만 잡는다.
- `pdf_url` 이 있으면 E 의 재료가 된다.

**설계 메모** `collect/adapters/research_db.py` 에 `report_by_id(report_id)` 추가. `reports/extract.py::extract_facts(doc, hint_ticker, today, db_hint=None)` 에 힌트 인자 — DB 값은 `ReportFacts.sources` 에 "리서치 DB reports#96425" 로 출처 표기. 콘솔 미리보기 줄에 "DB ✓" 표시. 파일명에 id 가 없거나 DB 에 없으면 지금과 같다.

**확인** 13건 모두 id 가 있으니 바로 측정 가능: 본문 추출값 vs DB 값 불일치 건수.

**비용·위험** 작다. DB 는 읽기 전용(`mode=ro`) 유지. 사용자가 파일 이름을 바꾸면 효과 없음 — 그래도 본문 추출이 남아 있다.

### C. 기존 맵에 새 리포트 증분 반영 (우선 3)

**문제** 지금은 "리포트 n건 → A 맵 초안" 한 방향이다. 같은 날 다시 돌리면 같은 map_id 로 덮어쓰고(NAVER Bear 287 수정에는 유용했다), 다른 날 돌리면 새 A 맵이 생긴다. 실제 운영은 "맵은 이미 있고, 오늘 리포트가 2건 더 나왔다" 인데 이 경우 사용자의 손 수정(내 추정, 확률, BUY 판단)이 사라지면 안 된다.

**방법** `mindmap draft --reports … --into A:005930:2026-10-20` (콘솔: 맵을 고른 상태에서 「리포트 추가 반영…」):
- A 맵의 draft 태그가 **남아 있는** 노드만 새 digest 로 갱신(A2.1 컨센 요약, A3.6.3 리비전, A8 재무 요약). 사용자가 손댄 노드(draft 태그 제거됨)는 건드리지 않고 "컨센 변화" 메모만 붙인다.
- 새 리포트에서 나온 TP 변경·의견 변경·실적 발표 문장은 **B 맵이 있으면** B 맵 사실 로그(B2)·이벤트(B3)로 넣는다 — 이미 있는 이벤트 분류기(`collect/classify`) 와 라이프사이클(§7) 을 탄다.
- 드라이버 컨센(A1.x consensus)이 바뀌면 값은 바꾸되 이전 값을 `history` 에 남기고, Kill 기준은 사용자 확정값이면 유지.

**설계 메모** `generate/merge.py` (새 파일): `merge_digest_into_map(m, digest, *, today) -> MergeResult(changed, kept, events)`. 변경 규칙은 `meta.draft.locked_nodes` + draft 태그로 판정. ops 에 `ops.merge_reports(map_id, paths, f)`. 테스트는 픽스처 3건으로 만든 맵에 가상 4번째 리포트(TP 상향) 를 넣어 A2.1·A3.6.3 만 바뀌고 A3.x 확률·A6 판단은 그대로인지.

**확인** 손 수정 노드가 보존되는지(테스트), 사용자 체감(두산처럼 리포트가 계속 나오는 종목).

**비용·위험** 중간. "무엇을 덮어도 되는가" 의 규칙이 핵심이고, 틀리면 사용자 판단을 지운다 — 보수적으로(draft 태그가 있는 노드만) 시작.

### D. 증권사별 추정치 분산·이견 표 (우선 4)

**문제** A8 재무 요약은 증권사 평균 한 줄이다. 삼성전자 2027E 영업이익은 IBK·유진·DS 가 꽤 다를 텐데(TP 460k vs 560k) 평균 605.6조만 보인다. Bear/Bull 앵커도 TP 분포로만 만든다.

**방법** digest 가 이미 리포트별 `estimates` 를 갖고 있다. 지표(영업이익·매출·EPS)×연도별로 min / max / 표준편차 / 증권사 수를 계산해
- A8.1.x 에 "컨센 범위" 줄 추가(예: `2027E OP 605.6조 (DS 650 ~ IBK 560, 3사)`),
- A3 앵커에 선택지 추가: Bear 는 **최저 추정 증권사의 TP**, Bull 은 최고 — 지금의 TP 분위수 방식과 메모로 비교,
- 분산이 크면(CV > 25%) 깃발 "증권사 간 이견 큼 — 가정 차이를 A2.2 에 적어라".

**설계 메모** `reports/digest.py::ReportDigest.spread(metric, col) -> (min, max, std, n, brokers)`; `generate/rules.py::fill_exec` 에 줄 추가; `generate/check.py` 에 CV 깃발. 렌더는 기존 `estimates_table` 아래 한 줄.

**확인** 삼성전자 3건·NAVER 6건 수치 눈으로 확인, 단위 테스트.

**비용·위험** 작다.

### E. 리포트 자동 내려받기 (M1, 우선 5)

**문제** 지금은 사용자가 PDF 를 받아 폴더에 넣는다. 리서치 DB 에 종목별 리포트 3.5만 건의 `pdf_url` 이 있다.

**방법** `mindmap draft --ticker 005930 --since 60d` → DB 에서 최근 60일 리포트 목록 → `pdf_url` 다운로드(`data/reports/<종목>/<broker>_<id>.pdf`, 이미 있으면 재사용) → 지금의 파일 경로. 콘솔은 「DB 에서 리포트 가져오기…」 단계에서 목록을 체크박스로 보여 주고 고른 것만 받는다.

**설계 메모** `collect/fetch_reports.py` (urllib, 재시도 2회, 5초, User-Agent, 실패 건은 건너뛰고 보고). `KSTOCK_OFFLINE=1` 이면 캐시된 파일만. 계획서 M1 과 같다.

**확인** Windows 에서만 가능(샌드박스·VM 은 프록시 403). 한경 PDF 가 로그인/쿠키를 요구하면 사용자 브라우저 다운로드로 폴백 안내.

**비용·위험** 중간. 네트워크·사이트 정책 의존 — 실패해도 지금 경로(파일 선택)는 그대로.

### F. 평가 루프 (M6, 우선 6)

**문제** "개선" 이 정말 개선인지 숫자가 없다. 지금은 테스트(104건)와 눈이다.

**방법** 골든 세트 둘:
1. **추출 정답표** — 실제 13건에 대해 증권사·날짜·의견·TP·직전 TP·현재가·52주·제목·표 (매출/OP/EPS 2025A~2027E) 정답을 JSON 으로 적어 두고(`tests/golden/extract/*.json`, PDF 는 저작권 때문에 저장소 밖 — 경로만), `mindmap eval-extract data/reports` 가 필드별 정확도를 찍는다.
2. **맵 정답** — 손으로 만든 삼성전자 맵(`examples/samsung_005930`) 처럼 사용자가 확정한 맵과 초안을 비교: 드라이버 지표 일치율, Base 앵커 오차(%), 리스크 상위 3개 겹침, 사람이 바꾼 노드 수(= 수정률). 수정률이 내려가면 개선.

**설계 메모** `generate/evals.py` (계획서 M6). 정답표 작성은 한 종목 20분 — 13건이면 반나절.

**비용·위험** 중간. 정답표 유지 비용. 그러나 이후 모든 개선의 근거가 된다.

### G. 사업부 표 → 섹터 KPI 드라이버 (우선 7)

**문제** 드라이버는 표에서 나오는 영업이익·매출·EPS 다. 투자 논제의 진짜 변수(삼성전자 HBM 비중, 두산 수주잔고·가스터빈 수주, NAVER AI DC 계약·광고 성장률) 는 리포트의 사업부 표와 본문에 있는데 `kpi_catalog` 의 섹터 KPI 는 이름만 있고 값이 안 채워진다.

**방法** 표 파서가 "매출액/영업이익" 외에 **사업부 행**(DS/DX/MX, 원자력/가스터빈, 서치플랫폼/커머스) 을 읽어 `segments[name][col]` 로 보관하고, LLM 그룹 drivers 가 섹터 KPI 후보와 사업부 숫자를 연결하게 한다(지금 프롬프트에 `kpi_candidates` 는 넘기지만 재료 숫자가 없다). 규칙만으로는 "사업부 영업이익 비중" 정도까지.

**설계 메모** `reports/extract.py::parse_segment_tables` (행 라벨 사전은 섹터별), digest 평균, prompts materials 에 사업부 표 포함. A 가 선행.

**비용·위험** 크다. 사업부 표 양식은 증권사마다 다르다 — 골든(F) 없이 시작하면 측정이 안 된다.

### H. '내 추정' 기본값 (우선 8, 사용자 결정)

지금 A1.x `mine` 은 컨센과 같은 값에 draft 표시다. 장점: 계산(A3·A6)이 바로 돈다. 단점: "내 추정" 이 내 것이 아닌데 숫자가 있어 확정한 것처럼 보일 수 있다. 선택지: (1) 지금대로 + ✎ 표시, (2) 빈칸 + 계산은 컨센으로 임시, (3) 설정으로 선택. 코드 변경은 아주 작다(`rules.fill_drivers`, 설정 키 `draft.mine_default`). **사용자 결정 필요** (Claude 문서 코멘트에도 같은 질문).

### I. 리포트 최신성 가중·오래된 리포트 처리 (우선 9)

**문제** 두산의 7/30 리포트(TP 110k, 이후 하나증권이 165k→120k 로 하향)가 10월 컨센에 같은 무게로 들어간다. 메리츠 NAVER 는 9/21·10/8 두 건이 모두 TP 330k 로 들어가 중앙값을 끌어당긴다.

**방법** (1) **증권사별 최신 1건** 만 TP·추정치 집계에 쓴다(오래된 것은 리비전 추적용으로만). (2) 기준일에서 45일 넘은 리포트는 집계에서 빼고 "참고" 로 표시(대화상자에서 △). (3) 가중 평균은 하지 않는다 — 설명하기 어렵다. 날짜 폭 경고(1차 완료)가 이미 있으니 그 다음 단계.

**설계 메모** `digest.build(..., latest_per_broker=True, max_age_days=45)`; 미리보기 줄에 "집계 제외" 표시. 테스트: 메리츠 2건 → TP 5건 집계.

**비용·위험** 작다. "제외" 는 사용자가 끌 수 있어야 한다(옵션).

### J. OpenAI 호환 GroupFiller (우선 10)

`.env` 에 `LLM_BASE_URL/LLM_API_KEY/LLM_MODEL`(spark vLLM) 이 있다. `GroupFiller` 는 Protocol(`complete(system, user) -> str`) 이라 `OpenAICompatFiller` 하나(urllib, `/v1/chat/completions`, JSON 모드) 를 더하면 로컬 LLM 으로 비용 없이 초안을 만들 수 있다. 환각 방어는 모델과 무관하게 동작한다. 작은 모델은 JSON 형식을 깨기 쉬우니 `parse_json` 의 복구(코드펜스 제거·첫 `{`~마지막 `}`)를 유지하고 그룹별 재시도 1회. 선택: `--llm claude|local`.

### K. 스캔 PDF OCR (우선 11)

글자 없는 PDF(`MIN_CHARS=200` 미만) 는 지금 경고로 끝난다. `pdftoppm` + `tesseract --lang kor+eng` 가 있으면 OCR 로 텍스트를 만들고 `extractor="ocr"` 로 표시, 표는 신뢰도 낮음으로 표 점수 감점. 한경 PDF 는 대부분 텍스트가 있어 빈도는 낮다 — 뒤로.

### L. 소소한 것 모음

- **L1 깃발 문구** EPS 비율 깃발은 "컨센/현재 비율 11.8 — 급증이 맞는지(단위·분기/연간 혼동 아닌지) 확인" 정도로 완화. 비율이 크면서 매출 비율도 함께 크면(진짜 급증) 깃발을 낮춘다.
- **L2 분기 라벨** `3Q26P`(잠정) 는 실적(A) 으로 보는데, 10월 초 리포트의 `3Q26E` 가 잠정 발표 뒤에도 E 로 남아 있으면 "최근 실적" 이 2Q 가 된다. 발표일(통상 분기 말 +8일) 이 지났고 본문에 "잠정실적" 이 있으면 A 로 승격.
- **L3 교차검증 확장** Base 가 Bull 과 2% 이내로 붙으면(두산 111,300 vs 114,000) "Base/Bull 이 거의 같다 — 분포가 좁거나 리포트가 적다" 깃발; TP 가 3건 미만이면 앵커 확률을 Bear 쪽으로 보수화(35/45/20).
- **L4 컨센 요약(A2.1)** 에 증권사별 TP 변화 화살표(165k→120k) 와 날짜를 넣어 리비전 방향이 바로 보이게. `tp_history` 가 있는 리포트는 "최근 12개월 TP 궤적" 한 줄.
- **L5 UI** 초안 생성 뒤 「이전 맵과 비교」 (같은 종목의 직전 A 맵과 A1/A3/A4 차이 표). 미리보기 대화상자에서 리포트 체크 해제(집계 제외).
- **L6 섹터 추정** `guess_sector` 점수(두산 48, NAVER 58)가 낮을 때는 리서치 DB 업종으로 보강(symbols.csv 에 섹터 열).
- **L7 로그** 초안마다 `data/out/draft_<map_id>.log` 에 요약·깃발·메모 저장 — 사용자가 나중에 "왜 이 값이었나" 를 추적.

## 4. 제안 순서

1. **지금 바로**: `.env` 키 확인 → 실제 13건으로 LLM 켜고 한 번 생성(A-1) → 결과를 보고 A-2(문장 분류 LLM) 착수. 함께 B(DB 교차 확인, 반나절).
2. **다음**: D(분산 표) + I(최신 1건·45일) + L1~L3 — 모두 작고 서로 독립.
3. **그 다음**: C(증분 반영) — 설계 합의 후. F(평가 루프) 를 같은 스프린트에 넣어 C 이후의 변화를 측정.
4. **뒤로**: E(자동 내려받기, Windows 에서 확인), G(사업부 KPI, A·F 뒤), J(로컬 LLM), K(OCR).

## 5. 열린 질문 (사용자 결정)

1. **H — '내 추정' 기본값**: 컨센 복사(지금) / 빈칸 / 설정.
2. **I — 오래된 리포트**: 45일 기준이 맞나, 증권사별 최신 1건만 쓰는 것에 동의하나.
3. **C — 덮어쓰기 범위**: draft 태그가 남은 노드만 갱신(보수적) 으로 시작해도 되나.
4. **E — 한경 PDF 다운로드**가 로그인 없이 되는지(브라우저에서 `pdf_url` 직접 열어 확인).
5. 네이버 실시간 조회가 Windows 에서 실제로 동작하는지 (대화상자 「현재가를 작성 시점 기준으로 조회」 켠 채 생성 → 요약에 "네이버 금융 … 종가/장중" 출처가 찍히면 OK).
