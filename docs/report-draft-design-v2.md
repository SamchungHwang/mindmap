# 증권사 리포트 → 투자 마인드맵: 설계 v2 (검토의견 반영)

작성 2026-10-21 · 입력: 사용자 첨부 「증권사 리포트 기반 투자 마인드맵 전면 재설계안」(mindmap-review1) · 앞선 문서 `report-draft-improvements.md`(개선안 A~L)

## 0. 결론 먼저

검토의견의 **방향에는 동의**한다 — 평균이 아니라 이견의 구조, 문장이 아니라 투자 주장, 목표가 분포와 시나리오의 분리, 의미는 LLM·숫자와 구조는 코드, 덮어쓰기 대신 변경안, 구현보다 정답표. 다섯 가지 모두 지금 코드에서 **구현 가능**하고, 그중 셋(수치 집계 규칙·시나리오 분리·변경안 흐름)은 LLM 없이도 된다.

"전면 재설계" 라는 말에는 동의하지 않는다. 지금 파이프라인(파일 읽기 → 추출 → 합산 → 규칙 채움 → LLM 그룹 → 교차검증 → 엔진 → 콘솔)에서 **읽기·숫자 추출·수치 집계·검증·엔진·저장·콘솔은 그대로 쓴다**. 바뀌는 것은 가운데 층 하나 — "문장 n개를 키워드로 분류해 노드에 꽂는" 단계가 "리포트별 투자 주장(Claim)을 뽑고 증권사 간 쟁점(Issue)으로 묶은 뒤 노드로 매핑하는" 단계로 바뀐다 — 와 시나리오 노드의 의미, 그리고 새 리포트가 왔을 때의 동작이다. 코드로는 새 모듈 3개(`claims`·`issues`·`changes`)와 `rules`·`check`·엔진의 수정이고, 삭제되는 것은 거의 없다.

**선행 조건이 하나 있다.** 주장 추출(P2)과 통합(P3)은 LLM 없이는 안 된다. 지금 `.env` 의 Anthropic 키는 형식이 맞지 않아(`apikey_…`) 그룹 채움이 전부 실패하고 있다. 키를 고치거나, `.env` 에 있는 spark vLLM(OpenAI 호환)용 필러를 먼저 붙여야 P2 부터 진행된다. 이것이 1순위 작업이다.

## 1. 검토의견 항목별 판정

### §2 '문장' 이 아니라 '투자 주장(Claim)' — 동의, 구현 가능 (LLM 필수)

지금은 `reports/extract.py::extract_sentences` 가 문장에 키워드 점수를 매겨 kind(thesis/risk/catalyst/…)를 붙인다. 실제 13건에서 리스크 상위 3개 중 1~2개가 리스크가 아닌 문장이었다. 주장 단위로 바꾸면 이 문제가 근본적으로 풀리고, 증권사 간 비교가 가능해진다.

데이터 모델(검토의견 표 + 내가 더한 것):

```
Claim {
  id, report_id, broker, date, page,
  text            # 주장 한 문장 (LLM 이 정리)
  kind            # forecast(전망) | fact(사실) | opinion(의견) | revision_reason(변경 사유) | risk | catalyst | valuation
  driver          # 핵심 변수 — 정규화된 이름 (예: HBM4 공급량, 가스터빈 수주, 광고 매출 성장률)
  target          # 영향 대상 (예: 메모리 영업이익, 2027E EPS, 목표 PER)
  direction       # + | - | 0
  horizon         # 2027E | 4Q26 | 2026-10-30 | null
  stance          # 컨센 대비: 강세 | 약세 | 중립 | 불명 (통합 단계에서 채움)
  quant           # 주장이 기대는 숫자 — 표/본문에 있는 값만 {metric, col, value, source}
  evidence        # 원문 인용 (리포트 텍스트에 그대로 있어야 한다 — 없으면 주장 폐기)
  inferred        # LLM 이 리포트에 없는 인과를 보탰으면 true → 별도 표시, 노드에는 안 들어감
}
```

구현 메모:
- `reports/loader.py` — 페이지 경계를 보존한다(`ReportDoc.pages: list[(start, end)]`). 지금은 페이지를 이어붙여 page 를 잃는다. pypdf·pdfminer 모두 페이지 단위 추출이 가능하다.
- 섹션 인식 청킹: 한국 리포트는 표지 「투자포인트」 번호 목록 → 실적 전망 → 밸류에이션 → 리스크 순이다. 소제목으로 잘라 LLM 에 넣고 `section` 을 claim 에 남긴다. 「투자포인트」 목록은 사실상 주장 목록이라 재현율이 높다.
- 호출 수: 리포트당 1회(입력 8~12k 토큰), 13건이면 13회. 기존 `GroupFiller` Protocol 로 Claude·Mock·(새) OpenAI 호환 필러 모두 사용.
- 환각 방어는 기존 장치를 그대로 쓴다: `evidence` 는 공백 정규화 후 원문에 그대로 있어야 하고(`llm_fill.evidence_in`), `quant.value` 는 표(`estimates`) 나 인용문 안의 숫자여야 한다. 둘 중 하나라도 어긋나면 그 주장은 버린다. 그래서 "환각률" 은 측정 지표가 아니라 **구조상 0** 이어야 한다.
- `driver` 이름 정규화가 통합의 열쇠다. `generate/kpi_catalog.py` 의 섹터 KPI 사전을 정규화 사전으로 확장한다(동의어: HBM 비중/HBM 매출 비중/HBM mix → `hbm_mix`).
- LLM 이 없으면 지금의 문장 방식으로 폴백한다(품질은 낮지만 초안은 나온다).

### §3.1 수치 통합 — 동의, 코드로 됨 (LLM 불필요)

검토의견의 다섯 규칙은 전부 `reports/digest.py` 에서 처리할 수 있다.

- **증권사별 최신 1건을 대표값으로** — digest 가 리포트별 `ReportFacts` 를 다 가지고 있어 `latest_per_broker=True` 한 줄 규칙이다. 메리츠 NAVER 2건(9/21·10/8, TP 330k 두 번) 이 바로 이 경우.
- **과거 리포트는 리비전 이력으로** — `tp_history`(투자의견 변동 내역 표) 를 이미 읽는다. 여기에 "같은 증권사의 이전 리포트" 를 더해 A3.6.3·A7.2 로 보낸다.
- **같은 기준만 집계** — 행 라벨의 `(지배)`·`지배주주`, 표 머리의 `K-IFRS 연결/별도` 를 `basis` 태그로 남기고, 같은 basis 끼리만 평균한다. 한국 리포트는 거의 연결·지배주주 EPS 라 충돌은 드물지만 순이익(전체 vs 지배)은 섞인다.
- **평균·중앙·최소·최대·표본 수** — `ReportDigest.spread(metric, col)` 추가(개선안 D).
- **실적 발표 이전 전망은 별도 표시** — 리포트 날짜가 직전 분기 잠정실적(분기 말 +8일 전후) 보다 앞이면 "실적 전" 태그. 두산 7/30·8/3 리포트가 그 예(2Q 발표 전). 45일 넘은 리포트는 집계에서 빼고 참고로만(옵션).
- 가중평균(StarMine 식 정확도 가중)은 하지 않는다 — 동의. 설명할 수 없는 숫자를 만든다.

### §3.2 투자 논거 통합(공통·이견·독립·미해결) — 동의, LLM + 코드 검증

주장들을 `driver` 로 묶은 뒤 네 분류를 **코드가 판정**하고 LLM 은 이름·한 줄 요약만 붙인다.

- 공통 견해: 서로 다른 증권사 2곳 이상이 같은 driver·같은 direction.
- 핵심 이견: 같은 driver 에 direction 이 반대이거나, `quant` 가 연결된 수치의 차이가 25% 이상(2027E 영업이익 2.4조 vs 3.5조).
- 독립 주장: 1곳만 말했지만 `quant` 가 있거나 선행지표(수주·가동·인증·계약) 를 들었다 — 점수로 올린다. 검토의견의 "언급 횟수보다 근거의 구체성" 을 점수로 바꾼 것.
- 미해결 쟁점: 방향이 갈리는데 어느 쪽도 숫자가 없거나, 리포트가 "불확실·확인 필요" 라고 쓴 것.

LLM 묶기의 비결정성은 (1) claim 을 저장하고 issue 에 안정적 id(driver 이름 기반)를 주고, (2) 재실행 시 이전 issue 와 diff 를 보여 주는 것으로 다룬다. 작은 로컬 모델은 추출은 되지만 통합은 약할 수 있어, 통합의 1차 묶기는 코드(driver·direction) 로 하고 LLM 은 보조로 둔다.

### §3.3 전망 변화(리비전) 설명 — 부분 가능, 정직하게 제한

"왜 바뀌었나" 는 두 경로로만 답한다.

1. 리포트가 사유를 적었으면 그 문장을 인용한다(`kind=revision_reason`). 하나증권 두산 165k→120k 처럼 리포트 본문에 보통 한 문단이 있다.
2. 같은 증권사의 이전 리포트가 **함께 입력돼 있으면** TP = EPS × 목표 PER 로 분해해 "EPS 변화 vs 배수 변화" 를 계산한다(목표 PER 은 밸류에이션 문장 "PER 12배 적용" 에서 읽는다 — 정규식으로 가능).

둘 다 없으면 **"상향/하향 사유 확인 불가"** 로 쓴다. 리서치 DB 에는 `prev_target_price` 는 있지만 이전 EPS 가 없어 DB 만으로는 분해가 안 된다. 검토의견의 "AI 가 임의로 설명하면 안 된다" 에 전적으로 동의.

### §4 맵 구조 — A0~A8 유지, 템플릿 변경 없이 가능

검토의견은 A2 를 "컨센서스와 이견", A7 을 "전망 변화 추적" 으로 바꾸자고 한다. 템플릿 v1.0(§3.2) 과 맞춰 보면 **노드 정의를 바꾸지 않고도** 담을 수 있다.

- **A2.1 내재 가정(estimate)** 의 하위로 `A2.1.1 공통 견해 · A2.1.2 핵심 이견 · A2.1.3 독립 주장 · A2.1.4 미해결 쟁점` 을 둔다. 각 항목은 issue 하나이고 `links` 로 A1.x 드라이버와 근거 claim(A8) 을 가리킨다. "현재 주가가 성립하려면 시장이 믿어야 하는 것" 을 증권사 n곳의 견해로 근사하는 것이니 템플릿의 질문과도 맞다.
- **A2.2 내 뷰 · A2.3 시장이 틀린 이유(judgment)** 는 **비워 둔다**. 검토의견처럼 A2 전체를 컨센서스 구조로 바꾸면 사용자의 variant perception 자리가 사라진다. 초안은 "증권사들이 말하는 것" 의 정리이고, 다르게 보는 것은 사람이 쓴다 — 이 프로젝트의 원칙.
- **A7** 은 템플릿에 이미 `A7.2 업데이트 로그(event[])` 가 있다. 새 리포트·TP 리비전·추정치 변화는 A7.2 와 A3.6.3 으로 들어가면 되고, A7 의 이름을 바꿀 필요가 없다.
- **A1 ↔ A2 연결**: issue.driver 가 A1.x 이면 A2.1.x.links 에 A1.x 를, A1.x.links 에 관련 issue 를 넣는다. 렌더러(native) 가 links 를 점선으로 그릴 수 있다 — "원인과 의견 차이가 연결된 구조" 가 화면에 보인다.
- **A1 드라이버의 출처가 바뀐다**: 지금은 표에서 나오는 영업이익·매출·EPS 다. 주장이 쌓이면 "가장 많은 주장이 걸려 있고 숫자가 연결된 driver" 가 A1 후보가 된다(HBM4 공급, 가스터빈 수주). 표 지표가 아닌 변수는 `current`·`consensus` 를 리포트 본문 숫자(출처 표기)로 채우고, 없으면 질문 노드로 남긴다.

### §5 Bear/Base/Bull — 동의, 지금 방식에서 바꿀 것이 가장 많은 곳

지금은 목표가 분포로 세 시나리오를 만든다(Bear = 최저×0.9 또는 52주 저가, Base = 하위 1/3, Bull = 평균). 삼성전자 3건(460k~560k) 에서 Base 506k · Bull 517k 로 거의 같아졌다 — 검토의견 말대로 이것은 시나리오가 아니라 세 증권사의 차이다.

바꾸는 방법:

1. **목표가 분포는 A3.6 아래 별도 노드로** — `A3.6.4 증권사 목표가 분포`(min/median/mean/max/n/분산/리비전, fact). 리포트에서 바로 나온다.
2. **A3.1~3 은 세 경로로 채운다.** (a) 리포트가 Bull/Bear 케이스를 제시하면 그 값과 가정을 쓴다(일부 리포트는 "Bull case 60만원 / Bear case 30만원" 을 준다 — 정규식 추가). (b) 없으면 증권사별 **EPS × 목표 PER** 의 최솟값/중심/최댓값으로 계산하고 `valuation_method = "시스템 계산: min(EPS)×min(PER)"` 처럼 **시스템 계산치임을 노드에 적는다**. 증권사가 직접 제시한 목표가와 섞이지 않는다. (c) 그것도 못 하면 지금의 분포 기반 앵커를 폴백으로 쓰되 같은 표기를 한다. 현재의 Bear 하한(현재가 −40%) 은 (b)(c) 의 보정으로 유지.
3. **확률은 비워 둔다.** 30/45/25 기본값을 강제하지 않는다. 템플릿 §3.3 은 "세 시나리오 확률 합이 1.0 일 때만 완료, 미완료 맵의 A6.5 는 WATCH" 라고 이미 정해 두었으므로, 확률 공란 = 미완료 = WATCH 가 템플릿과 정확히 맞는다. 엔진(`engine/calc.py`) 이 확률 None 이면 A3.4·A3.5 를 "보류" 로 두도록 고친다. GUI 에는 「기본 확률 30/45/25 넣기」 버튼을 둬서 **사용자의 행위**로 기록되게 한다.

### §6 LLM 의 책임 분담 — 동의, 지금 구조와의 차이는 '어디서' 쓰느냐

검토의견의 표는 현재 아키텍처와 거의 같다(PDF 파서·규칙 숫자 추출·Python 집계·결정론 매핑·스키마 검증은 모두 있다). 차이는 하나: 지금은 LLM 이 **노드를 직접 채우고**(그룹 6개) 코드가 사후 검증하는데, 바꾸면 LLM 의 출력은 **Claim/Issue JSON** 이고 노드는 코드가 결정론적으로 만든다. 장점은 테스트 가능성(JSON 을 픽스처로), 재현성, 모든 노드 → 원문 역추적. 기존 그룹 채움은 Kill 조건 제안 같은 보조 용도와 폴백으로 남긴다.

비용: 리포트당 1회(추출) + 종목당 1~2회(통합·요약) — 13건이면 15회 안팎, 수십 초. 지금 그룹 6회보다 많지만 리포트 수에 비례할 뿐이다.

### §7 신규 리포트 — 동의, 개선안 C 를 '변경안' 방식으로 교체

내가 앞서 쓴 C(draft 태그 노드만 자동 갱신)보다 검토의견의 "변경 영향 분석 → V2 변경안 → 사용자 승인" 이 낫다. 자동으로 아무 노드도 바꾸지 않고, 바꿀 후보를 보여 주기 때문이다.

```
ChangeSet {
  base_map, new_reports,
  changes: [{ node_id, kind: 추정치 변화 | 새 주장 | 기존 논제와 충돌 | TP 리비전 | 새 리스크 | 새 촉매,
              before, after, evidence: [claim_id], user_touched: bool }],
  summary   # "컨센 OP 2027E 2.6→2.9조(+12%), 하나증권 TP 400k→420k 상향(사유: …), 새 쟁점 1(AI DC 수주 시점)"
}
```

GUI 「변경안 보기」 에서 체크해 승인하면 적용하고, A7.2 업데이트 로그에 이벤트를 쌓고, 이전 버전 파일을 `…v1.json` 으로 보존한다(`meta.version`). 사용자가 손댄 노드(`user_touched`) 는 후보로만 올리고 자동 적용 대상에서 뺀다. B 맵이 있으면 같은 ChangeSet 이 B2.4 사실 로그·B3 이벤트로도 간다 — 템플릿의 "스냅숏 불변성" 과 충돌하지 않는다.

### §8 우선순위 — 동의, 순서 하나만 조정

P0 정답표부터 — 동의. 단 범위를 정한다: 수치(증권사·날짜·의견·TP·직전 TP·현재가·52주·표 핵심 4지표×3개 연도)는 13건 전부, 주장은 리포트당 **핵심 주장 상위 5개** 와 리스크 3개만. 전수 정답은 비용이 과하다.

P1(추출·수치 표준화)은 이번 1차 수정으로 상당 부분 끝났다(제목 13/13, TP·현재가·표 읽힘 13/13). 남은 것은 basis 태그·최신 1건·분산.

**P2 앞에 P1.5 — LLM 경로 확보** 를 넣는다. Anthropic 키 수정, 또는 OpenAI 호환 필러(`OpenAICompatFiller`, `/v1/chat/completions`, JSON 모드) 로 `.env` 의 spark vLLM 연결. 반나절. 이것 없이는 P2·P3 가 시작되지 않는다.

평가 기준은 검토의견 다섯 개(주장 재현율·근거 정확도·이견 식별·수치 정확도·활용성)에 **환각 건수(= 0 이어야 함)** 와 **비용·시간** 을 더한다. "사용자 수정 노드 수" 는 보조 지표로 남긴다 — 활용성을 가장 싸게 재는 방법이기 때문이다.

### §9 차별화 셋 — 동의

Disagreement > Consensus, Causal structure > Summary, Evolving > Static. 세 번째는 템플릿의 A→B 라이프사이클·`history`·A7.2 가 이미 바탕이다.

## 2. 내가 더하는 것 (검토의견에 없는 것)

1. **한국 리포트의 구조를 쓴다.** 표지 「투자포인트」 번호 목록 → 주장 1차 후보. 리포트 종류(Preview/Review/인뎁스/NDR 후기/Company Brief)를 메타로 보존 — 인뎁스는 주장이 많고 Preview 는 분기 숫자 중심이다. 통합 때 종류별 가중은 하지 않지만 화면에 표시한다.
2. **리서치 DB 교차 확인(개선안 B)** 은 그대로 유효하다. 파일명의 한경 리포트 id 로 `reports`·`report_details` 와 대조해 추출 실수를 잡는다. 정답표(P0) 작성도 DB 값으로 시작하면 빨라진다.
3. **사용자 판단 영역은 비운다.** A2.2·A2.3·A6.5·'내 추정' 은 초안이 채우지 않고 질문 노드로 남긴다(템플릿 `question` 철학). '내 추정' 기본값은 **빈칸**으로 바꾸는 쪽을 권한다 — 확률 공란과 같은 이유다. 계산은 컨센으로 임시 수행하고 "컨센 기준 임시 계산" 을 표기.
4. **출처 역추적을 1급 기능으로.** 모든 자동 노드는 `source` 에 `broker · date · page · claim_id` 를 갖고, GUI 에서 노드를 고르면 원문 인용이 뜨고 PDF 페이지를 연다(`os.startfile` 로 PDF 열기 + 페이지는 뷰어 의존). 검토의견 §6 마지막 문장을 기능으로 옮긴 것.
5. **섹터 KPI 사전을 driver 정규화 사전으로.** 통합의 정확도는 "같은 변수를 같은 이름으로 부르는가" 에 달려 있다. 13건에서 나온 driver 이름을 모아 사전을 만들고(반도체·인터넷·원전/에너지부터), 모르는 이름은 LLM 이 가까운 항목에 매핑하되 `normalized=false` 로 표시.
6. **기능보다 정답표.** P0 이 끝나기 전에는 추출·주장 로직을 더 바꾸지 않는다. 눈으로 보는 개선은 이미 한계에 왔다.

## 4. 단계와 완료 기준

|---|---|---|---|
| P0 | 실제 13건 정답표: 수치 전부 + 핵심 주장 5·리스크 3 /리포트 (`tests/golden/`, PDF 는 저장소 밖) | `mindmap eval-extract` 가 필드별 정확도 표를 찍음 | 1~2일 |

## 5. 사용자 결정이 필요한 것

1. '내 추정' 기본값을 빈칸으로 바꾸는 데 동의하는가 (지금: 컨센 복사 + 초안 표시).
2. 시나리오 확률 공란 → 기대수익률·손익비 "보류" 로 가는 데 동의하는가 (지금: 30/45/25 기본값).
3. LLM 경로: Anthropic 키 수정 vs spark vLLM(OpenAI 호환) 먼저.
4. P0 정답표의 주장 정답은 누가 쓰나 — 내가 초안을 만들고 사용자가 고치는 방식을 제안.
